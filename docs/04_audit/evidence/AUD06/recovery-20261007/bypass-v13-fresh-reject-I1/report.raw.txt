**I1-Q13-01 — P1 — object rest perde propriedades armazenadas, referências e callable/default.**

Local: `scripts/phase11-bypass-audit.mjs:169`, especialmente 176–197; consumidores em 232–250 e 1167–1244. `objectRest` percorre somente propriedades do literal original e não projeta propriedades registradas em `assignedProperties`. O container sintético pode ficar vazio apesar de conter, em JavaScript, o valor já armazenado. Isso permite inferir SQL de referência concretamente exposta à mutação e aplicar default puro a um callable definido.

Contrato: SPEC linhas 291–309 e 317–326: seleção/destructuring transportam origens armazenadas; valor definido preserva origem; exposição de container invalida referências alcançáveis; cópia rasa mantém referências internas. Nenhuma análise universal ou computação dinâmica é necessária nestes exemplos.

Prova mínima, fixture `apps/api/src/postgres-rate-limit.ts`:

```ts
const q={text:"SELECT 1"};
const box={}; box.x=q; const {...copy}=box;
function rewrite(b){b.x.text="DELETE FROM appointments";}
rewrite(copy);
client.query(q);
```

`copy.x === q`: a atribuição muda exatamente o argumento de `client.query`. CLI atual retorna **exit 0, PASS, findings []**, inclusive no replay. O scanner deveria recusar a inferência, pois `q` escapou; a escrita resultante é de agendamento e não é quota.

Par benigno: trocar `box.x=q` por `box.x=q.text` e alterar somente propriedades primitivas da cópia mantém `q.text="SELECT 1"`: **exit 0, PASS**. Controle com `box={x:q}` recusa corretamente: **exit 1, unresolved_query_expression**. A diferença é o armazenamento, não o efeito ou o caminho.

Outra prova direta da mesma falha:

```ts
const b={}; b.f=fetch; const {...c}=b;
const {f=()=>1}=c;
f("x");
```

`f` é `fetch`, porque a propriedade está definida; o default não se aplica. CLI **exit 0, PASS**. Par `b.f=()=>1`: **exit 0, PASS**. Variante com `b={f:fetch}`: **exit 1, direct_fetch**. Também houve PASS com a função query bindada a `DELETE FROM appointments` armazenada antes de rest/default.
